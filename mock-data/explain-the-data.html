Demo talking guide

How to explain the demo data

A simple, plain-English guide to the mock data in the Incident Manager. Use it before a demo so the numbers, screens, and the three special incidents all make sense — to you and to the people watching.

01The 30-second story

If you only have time to say one thing, say this:

"This is a made-up but realistic set of 19 incidents from a fictional company. They were loaded through the real API, so the app behaves exactly as it would with production data — live counts, timelines, filters, and analytics all work. We use it to demo the product without needing real customer data."

02What the data is

  • It's fictional. No real company, no real customers, no real incidents.
  • It's realistic. The stories are the kind small teams actually hit: outages, slow services, expired certificates, bad deploys.
  • It's loaded through the real API — so events, timelines, and dashboard numbers behave like production.
  • Every incident has a status and a severity, and most have a start time, sometimes an end time, a root cause, and a resolution.
  • Each status has a full story. Think of each incident as a real mini-crisis that already happened.

04The four statuses

A status answers: "Where is this incident right now?"

Open

The problem is happening right now and nobody is working on it yet. It's the "just created, needs attention" state.

Investigating

A human is on it. The team has started digging in, but there's no fix yet.

Resolved

The problem is fixed. There's a recorded root cause and a resolution, and it's still on the board for review.

Closed

Done and filed away. The whole story is saved as history — useful for lookups and learning.

05The four severities

A severity answers: "How big is the problem?" Red is worst.

Critical

Money or customers are being hurt right now — e.g. checkout is failing or logins are broken.

High

Major impact but not total — e.g. a key service is erroring or slow.

Medium

Noticeable but limited impact — e.g. a service is slower than normal or one feature misbehaves.

Low

Minor annoyance — e.g. slight delays, cosmetic problems, or small backlogs.

06Three special incidents to point at

These three were added on purpose. Each one proves the app handles real-world edge cases.

Medium Open
1. Stale API keys in rotation — "open" for ~90 days.

What to say: "Not every incident is urgent. This one has been open for months — long-running security debt. Watch how the dashboard and lists handle a very old, still-unresolved item without treating it like a fresh alert."

Low Resolved
2. Background job crashed and recovered — no description and no services listed.

What to say: "Real incidents often arrive with missing info. This one has a title and a fix, but no description and no affected services. The app still shows it cleanly — nothing breaks, nothing looks broken."

High Resolved
3. Upload service disk full — resolved today.

What to say: "This one keeps the 'Resolved Today' number honest. Its end time lands on today's date, so it drives that KPI — a small but real story: the disk filled up during the nightly backup."

07What each screen shows

Dashboard
  • Points at the KPI cards: 9 active, 2 critical, 6 resolved today, ~3h MTTR.
  • Say: "Every number here is computed live from the incidents — nothing is hard-coded."
Incidents list
  • Use the filters to show only critical, then only resolved.
  • Say: "Filters run against the API, so you can slice the data any way."
Incident detail (e.g. "Full production outage")
  • Open its timeline: open → investigating → resolved → closed, plus root cause and resolution.
  • Say: "Every status change is recorded as a real timeline event, the way it'd happen in production."
Logs & Analytics
  • Logs page shows live sample log lines; pause the stream to freeze it.
  • Analytics shows real derived numbers: time to resolve, how often incidents happen, which services are busiest.
Security Checker
  • If you scan a repository, the story ties in: "Stale API keys in rotation" is the kind of finding a scan surfaces.

09Before the demo

  • Load the data the same day as the demo, so "Resolved Today" is correct.
  • Start the backend (uvicorn app.main:app) and the frontend (npm run start).
  • Open Dashboard first — the KPI cards tell the story instantly.
  • Then Incidents (play with filters) and one incident detail page with a timeline.
  • Expect: 19 total incidents, Active 9, Critical 2, Resolved today 6.
